# Проверки перед переносом на VPS

## Вход сотрудников

Исправлено сохранение неверных попыток `/control/login/verify`: увеличение счётчика фиксируется транзакцией, после чего возвращается 401. Раньше исключение внутри транзакции откатывало счётчик; воспроизводящий тест получил `0` вместо `1`. Пять попыток исчерпывают конкретный challenge, даже правильный код после этого не выдаёт cookie или токен. Одновременные запросы используют прежний `FOR UPDATE`. Успешный вход, код с ведущими нулями, запрет повторного использования, истечение, отключённый сотрудник и ошибки формата проверяются регрессией.

Свежая независимая проверка кандидата не обнаружила обходов в исправлении. Настройки MFA и значение по умолчанию **не изменены**: защита остаётся выключенной до отдельного включения владельцем после VPS. Исправление не меняет транзакционный адаптер или ограничения запросов.

## Два ипотечных периода

Для семейного сценария длиннее 15 лет можно самостоятельно задать предполагаемую ставку второго периода. Без неё будущий платёж и переплата не показываются. Расчёт использует остаток льготного долга после 180 платежей, затем новый аннуитет на оставшийся срок. Рыночная часть комбинированного кредита продолжает рассчитываться по исходной рыночной ставке. Ставка, цена, взнос и срок сохраняются на устройстве. Точный минимум 20,1% и ручной ввод рублей сохранены.

Проверка сравнивает формулу остатка с независимой помесячной амортизацией и погашением обеих частей до нуля. Есть сценарии нулевой/неизменной/изменённой будущей ставки, неверных значений, короткого срока и недопустимого взноса. Это модель с заданными пользователем допущениями; она не заменяет предложение банка и не учитывает страховки, комиссии, досрочное погашение. Ставки и право на программы из текущих настроек этот пакет не пересматривает; перед реальными заявками их нужно подтвердить с банками.

Математическая основа: [аннуитет PMT](https://support.microsoft.com/en-us/office/pmt-function-0214da64-9a63-4996-bc20-214433fa6441). Неизвестная договорная переплата остаётся неизвестной; отдельная оценка называется «по сценарию».

## Напоминания о подтверждённых показах

- Клиент и назначенный менеджер получают сообщение бота за 24 часа и за 2 часа. Время в тексте — Владивосток. Ссылки открывают обращение/карточку.
- Только статус `confirmed` и открытое обращение. Запрос переноса сохраняет действующее подтверждённое время до решения менеджера; принятие переноса заменяет расписание.
- Расписание создаётся в той же транзакции, что изменение показа. Отмена, завершение, закрытие лида, смена ответственного/пользователя исключают старые сообщения. Перед отправкой ещё раз проверяются актуальные время, статус, получатель и аренда записи.
- Уникальный `dedup_key` предотвращает повторное создание при перезапуске worker. Отменённое, но ещё не отправленное расписание допускает повторное подтверждение того же будущего времени.
- Если показ подтверждён менее чем за 24 часа, пропущенное суточное напоминание не отправляется; менее чем за 2 часа — оба пропускаются. После простоя просроченный показ не создаёт напоминаний.
- Worker каждые 60 секунд восстанавливает пропущенные расписания, читая лиды страницами по 200. Существующие аренды, backoff и dead-letter после 8 попыток сохранены.

Нужны работающие API/worker/PostgreSQL, `BOT_TOKEN`, связанные Telegram ID и запуск бота получателями. GitHub Pages эти сообщения не отправляет. Проверки используют имитацию отправителя, не реальные сообщения. Telegram не даёт транзакции вместе с нашей БД: при обрыве после принятия сообщения Telegram, но до отметки обработки, повтор возможен. Отмена одновременно с уже начавшимся сетевым запросом не может отозвать этот запрос; новые и ещё не отправленные задания отзываются.

## Причины потери

Семь причин: недостаточно взноса, отказ ипотеки, отложенная покупка, другой объект/агент, нет связи, неподходящий запрос, другая причина. При «другой» обязательно уточнение. При статусе «Потерян» причина обязательна и проверяется сервером; детали — до 1000 символов. Повторная правка причины не меняет дату потери. Возврат в работу очищает причину и дату.

Отчёт считает всех клиентов со **текущим** статусом «Потерян» по дате потери, а не по дате создания и не по загруженной странице CRM. Менеджер получает только назначенных клиентов. Используются включительные календарные даты Владивостока, период до года. Исторические потери без даты показаны отдельно и не входят в период. Они не получают выдуманные даты или причины. Это отчёт текущих потерь, не история всех повторных переходов по воронке.

## Объём и воспроизводимость

```sh
npm run verify
npm run test:scale
npx playwright test
npx playwright test --config=playwright.finance-webkit.config.ts
```

`TEST_DATABASE_URL` запускает серверные тесты в отдельной схеме PostgreSQL. Без него — PGlite. Не использовать рабочую базу. CI запускает PostgreSQL 16, Chromium, мобильный WebKit и проверку Docker/Caddy.

Набор масштабирования: 1000 опубликованных ЖК + закрытый черновик, 3000 планировок, 5000 фото, 2000 клиентов, 50000 событий. Проверены последняя страница каталога, фильтры, поиск последнего клиента, полная карточка, отсутствие галерей в выдаче, отдельные планы в подборе, страницы CRM, полная аналитика, причины потери и права менеджера. Измерения печатаются как `SCALE_BENCHMARK` (7 последовательных запросов на операцию, медиана и максимум как оценка p95 малого набора). Это smoke-бенчмарк, не нагрузка одновременных клиентов.

Пример одиночного локального прогона PGlite: p95 страницы каталога 6,63 мс / 26 КБ; CRM клиентов 10,21 мс / 36 КБ; событий 37,35 мс / 12 КБ; аналитики 41,03 мс; данных подбора всех ЖК 103,96 мс / 1,66 МБ. На другом оборудовании результаты будут отличаться. Сетевую загрузку, реальные фото, карту 2GIS, Telegram и одновременную нагрузку нужно проверить после VPS.

Браузерные регрессии проверяют второй ипотечный период и причины потерь на 320/390/430 px, сохранение значений, ошибки и отсутствие горизонтального переполнения. Отдельный тест большого каталога проверяет 20 карточек сначала, 40 после догрузки и нахождение тысячного ЖК. Скриншоты новых экранов сохраняются в артефакт CI `pulse-prelaunch-review`.

## Перенос

Новая миграция `013_prelaunch_completion.sql` добавляет только поля/индексы, не удаляет данные. На VPS: резервная копия, миграции, затем API и worker из одной версии. До открытого запуска проверить восстановление резервной копии, импорт реального каталога, Telegram-доставку, юридические реквизиты, актуальные банковские условия и включить MFA владельцу с проверенным Telegram ID.
