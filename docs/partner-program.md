# Партнёрская программа PULSE.DV

## Где открыть

- Mini App: профиль → «Рекомендуйте PULSE», маршрут `#/partners`. На главной — компактная карточка после блока помощи с подбором. Нижняя навигация остаётся прежней.
- Control: «Работа» → «Партнёры», маршрут `#/partners`. В карточке лида видны пригласивший партнёр и ссылка на проверку/расчёты; ответственный менеджер учитывается отдельно.
- Покупатель: `#/partner-invite?code=…`. После перехода в каталог приглашение сохраняется в текущей сессии браузера; в любой стандартной форме заявки появится отдельное необязательное подтверждение рекомендации и передачи ограниченных статусов. Без этого подтверждения заявка обычная.

## Рабочий путь

1. Партнёр входит через подписанный Telegram Mini App, принимает актуальную версию условий и указывает свои имя/телефон. Сервер привязывает кабинет к проверенному Telegram ID. Повторное подключение не создаёт новый профиль.
2. Партнёр делится общей ссылкой либо создаёт персональное приглашение с собственной подписью для удобства. Телефон третьего лица не собирается. Создание или открытие ссылки ещё не закрепляет клиента.
3. Покупатель сам отправляет заявку и отдельно подтверждает рекомендацию. API атомарно записывает лид, владельца рекомендации, код приглашения, версию условий и публичное событие. Согласие и его время фиксируются в лиде; наличие рекомендации требует отдельного подтверждения в запросе.
4. Владелец связывается с покупателем, сверяет совпадения и подтверждает закрепление или выбирает причину отказа. Администратор может просматривать очередь; закрепление, начисление, отмена и запись выплаты — только владелец. Обычные менеджеры работают с назначенными лидами, не получают партнёрскую финансовую очередь.
5. Изменение этапа обычной карточки лида появляется в истории партнёра. Телефон покупателя, переписка, документы, ссылки на платежи и внутренняя заметка проверки в кабинет партнёра не выдаются; фамилия сокращается до инициала.
6. После статуса «Сделка»/«Закрыт» и фактического получения комиссии владелец проверяет и начисляет вознаграждение. Суммы фиксируются отдельной неизменяемой записью в копейках.
7. Партнёр запрашивает оформление выплаты и указывает статус получателя. Владелец проверяет договор и документы, выполняет перевод отдельно, затем фиксирует фактическую дату, удержания, ссылку/номер платежа и документы. Банковская операция этой кнопкой не выполняется. Итог перевода виден партнёру.

## Уникальность и ограничения

Сверяются нормализованный телефон (`8 999…`, `7 999…`, `+7 999…` → `+7999…`) и только подтверждённый Telegram ID. Более ранний прямой лид либо более ранняя незавершённая рекомендация показываются как совпадения. Владелец разбирает их до принятия. Рекомендацию, которую покупатель не подтвердил, можно отклонить как «Обращение не подтверждено»; она не мешает последующей подтверждённой рекомендации. Принятое закрепление повторно не назначается другому партнёру. Саморекомендация по проверенному Telegram или телефону партнёра запрещена.

API сериализует конкурирующие заявки/проверки advisory locks по идентификаторам покупателя. В БД уникальны принятые phone/user claims, один лид имеет одну рекомендацию, одно направление имеет только одно неотменённое начисление. Проверки и выплаты используют revision. Отпечаток исходной заявки проверяет повторный запрос независимо от последующих заметок менеджера. Повторный idempotency key заявки не меняет пригласившего партнёра, даже если ссылка после этого приостановлена. Повторная отправка выплаты не создаёт вторую выплату.

Это проверка относительно сохранённой CRM, а не универсальное установление личности. Другой номер/аккаунт, общие семейные телефоны и старые анонимизированные записи требуют ручного разбора. Более ранний действительный прямой клиент по умолчанию не считается новым; принять позднюю рекомендацию поверх такого совпадения интерфейс не позволяет. После срока минимизации данных закрытого/потерянного лида телефон, Telegram и приватные заметки стираются также из рекомендаций и claims. Проверка старых клиентов после этого ограничена оставшимися данными. Партнёрская учётная запись и финансовый журнал сохраняются отдельно для расчётов; универсальное удаление неактивных пользователей их не удаляет.

Начисление рассчитывается по правилам, сохранённым при создании рекомендации: комиссия × (1 − 6%) × 30%. Например: 100 000 ₽ → вычет 6 000 ₽ → база 94 000 ₽ → начисление 28 200 ₽. Это сумма **до налогов получателя**. 6% — вычет по условиям программы; приложение не определяет налоговый режим агентства или получателя. Удержания вводятся после проверки, автоматического НДФЛ нет. Статус «самозанятый» требует проверки допустимости конкретного договора. Условия экрана — описание программы, а не подготовленный юридический договор.

Пока действует начисление, комиссия, дата её поступления и состоявшаяся сделка заблокированы от несогласованного изменения. Неоплаченное начисление можно отменить с причиной, исправить первичные данные и начислить заново; история остаётся. Выплаченное начисление не отменяется этим интерфейсом. Возврат комиссии после выплаты требует отдельного документального разбора и корректировки учёта; автоматической обработки возвратов и частичных выплат в этой версии нет. Финансовый результат Control вычитает из поступлений полное партнёрское вознаграждение, включая удержанную часть, по фактической дате выплаты. Другие расходы/налоги агентства не учитываются.

## API / БД / выпуск

Миграция `016_partner_program.sql`: partner_profiles, partner_invitations, partner_referrals, partner_client_claims, partner_rewards, partner_referral_events. Отдельные индексы телефона/проверенного пользователя, журнал событий с порядковым номером, ledger с частичным уникальным индексом. Существующие лиды и финансы сохраняются.

Публичные методы: `/public/partner-program`, `/public/partner-invites/:code`.
Кабинет (visitor auth): `/me/partner`, `/me/partner/join`, `/me/partner/invitations`, `/me/partner/rewards/:id/request`.
Control: `/control/partners`, `/control/partner-referrals/:id`, `/control/leads/:id/partner`, `/control/partner-referrals/:id/review`, `/control/partner-referrals/:id/accrue`, `/control/partner-rewards/:id/pay`, `/control/partner-rewards/:id/void`.
Обычная `/leads` принимает referralCode + referralConsent=true. Произвольный partnerId/userId клиентом не принимается. Цены/менеджер/комиссия передаются прежними методами карточки лида.

На GitHub Pages приложения работают в деморежиме: данные только в localStorage этого браузера. Партнёрский кабинет, заявка и Control демонстрируют один сценарий в одном браузере; ссылка не переносит локальные данные на другое устройство.

Для реальной общей БД нужен существующий VPS runtime из `deploy/README.md`: обновить контейнеры, применить миграции до запуска новой версии API, собрать веб с `VITE_PULSE_MODE=api`, заполнить BOT_TOKEN и TELEGRAM_BOT_USERNAME. Main Mini App в BotFather должен указывать на реальный URL Mini App. Telegram-ссылка `https://t.me/<bot>?startapp=ref_<code>` передаёт start_param; экран не доверяет ему для определения владельца или прав доступа — код и покупатель проверяются API. Ссылка `?startapp=partners` открывает программу. Обычный браузер без подписанного Telegram может оставить заявку, но подключить партнёрский кабинет должен через Telegram.

Обновление экранов: кабинет и Control обновляются при возвращении на вкладку и каждые 30 секунд, после действий — сразу. Это периодический опрос API, не WebSocket.

Проверки: API на PostgreSQL/PGlite — подпись Telegram, доступы, отдельное согласие, конкурирующее закрепление, дубли, идемпотентность, точный расчёт, отмена/повторное начисление, двойная выплата, приватность и минимизация. Playwright Chromium/WebKit — UI путь от приглашения до выплаты на 320/390/430 px, общий стиль, возврат в существующую карточку и отсутствие горизонтального переполнения.
